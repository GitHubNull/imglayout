# 开发者教程 · 02 架构与约定

> 前置：[01 快速上手](01-快速上手.md)。与 [ai-agent/02](../ai-agent/02-架构与约定.md) 同主题，本篇更侧重设计决策的「为什么」。

## 技术选型与结构

桌面壳用 **Tauri 2**（Rust）：体积比 Electron 小一个数量级，导出渲染、图片编解码、文件打包这类重活在 Rust 侧有原生性能；UI 用 **Vue 3 + PrimeVue 4**，选 PrimeVue 是因为其组件齐全且支持暗色预设，与「PS 式暗灰工具」目标一致。

代码分两层工程：`src/frontend/`（pnpm workspace 成员）与 `src/backend/`（Tauri/Rust）。根 `package.json` 只是脚本转发，构建顺序由 `script/build.sh` 固定为前端 → 后端。

## 关键设计决策的来历

**为什么 `PhotoItem` 不能随意加字段？**
前端 `types/layout.ts` 与 Rust `model.rs` 是 serde 契约，`.imglayout` 项目包就是这个结构的 YAML。曾经/很容易犯的错是给前端单方面加显示字段，结果旧包打不开或字段静默丢失。所以派生量（如图层序号）一律 computed 派生、不落盘。

**为什么先 `snapshot()` 再变更？**
撤销栈存的是整份 `doc` 深拷贝，简单可靠（文档量级小，深拷贝代价可忽略）。历史上出现过「快照晚于变更导致撤销丢状态」的 bug，现在项目里所有修改点都遵循这一顺序，review 时重点看有没有漏。

**为什么图层面板排序不改 items 数组？**
items 数组次序就是叠放次序（PS 语义：末尾=最顶层）。按文件名排序只是视图重排——如果把数组也重排了，画布叠放关系就被视图悄悄改掉。所以排序是纯视图 computed，且排序激活时禁用拖拽，避免两种「排序」语义打架。

**为什么零告警是硬门禁？**
Rust clippy `-D warnings` 与 `fmt --check` 从第一天就开着。存量零告警意味着任何新告警都明确指向本次改动，CI 里无法甩锅给历史代码。

**为什么 UI 文案中文硬编码、不做 i18n？**
产品定位是中文用户的小工具，引入 i18n 框架的维护成本（key 管理、语言文件同步）远超收益。若未来要出海，届时再抽离。

## 测试哲学

- 纯函数（排版算法、快捷键映射、画布主题）全部有 spec，改算法先看 spec；
- 排版算法前后端**对拍**：`lib/layout/layout.spec.ts` 里同一组输入跑 TS 实现并核对 Rust 侧 fixtures；
- 组件测试覆盖交互契约（拖拽换算、撤销步数、禁用态），不追求 DOM 细节快照。

## 已知限制（登记在案）
